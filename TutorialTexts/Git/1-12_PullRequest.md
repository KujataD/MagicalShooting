# 【1-12】プルリクエストを出そう【1章：Git導入編】

1. クリア条件：featureブランチからdevelopへのプルリクエストを1本作れればOK！

2. featureブランチでの作業が終わりました。これをdevelopに合流させたいのですが、黙って合流させると他のメンバーは気づけません。
   そこで、**「この作業をdevelopに入れていいか」をチームに確認してもらう手続き**を踏みます。これがプルリクエストです。

   用語：プルリクエスト（Pull Request、略してPR）
   「自分の作業を取り込んでください」という依頼のこと。GitHub上に専用のページが作られ、そこで**変更内容の確認とコメントのやり取り**ができます。OKが出たら合流させます。

3. 流れはこうなります。

   1. 自分のfeatureブランチで作業を完成させる
   2. すぐdevelopに入れず、まずPRを作る
   3. 他のメンバーが内容を見て、気になる点があればコメントする
   4. 問題なければ合流させる（次回1-13でやります）

   ※このサークルでは全員が同じようにUnityとスクリプトを触ります。レビューする側も同じメンバーなので、**「専門家の審査」ではなく「お互いの確認」**だと思ってください。

4. まず、作業をプッシュします。1-09でやった操作です。
   Forkで自分のfeatureブランチにいることを確認して、コミット → **Push**。

   ※初回のプッシュ時は「Publish branch」のような表示になります。GitHub側にまだこのブランチが無いので、新しく作るという意味です。そのままPushでOK。

5. プッシュしたら、GitHubのリポジトリページをブラウザで開いてください。
   黄色い帯で「feature/○○ had recent pushes」と表示され、「Compare & pull request」という緑のボタンが出ているはずです。これを押します。

   ※出ていない場合は、上部メニューの「Pull requests」→「New pull request」からでもOKです。

6. 【最重要】合流先（base）の確認

   PR作成画面の上部に、こういう表示があります。

   ```
   base: main  ←  compare: feature/enemy-graphics
   ```

   **ここのbaseを `develop` に変更してください。**
   初期状態ではmainになっていることが多いですが、1-11のルール通り、featureはdevelopに合流させます。

   ```
   base: develop  ←  compare: feature/enemy-graphics   ⭕ これが正解
   ```

   ![PR作成画面（baseがdevelopになっている）](../git_images/1-12_pr_create.png)

7. タイトルと説明を書きます。

   - **タイトル**：何をしたか一言（例：「敵キャラのグラフィックを追加」）
   - **説明**：もう少し詳しく

   説明はこのテンプレートに沿って書けば十分です。

   ```markdown
   ## やったこと
   - 敵キャラ（お化け）の画像を3種類追加
   - Enemyプレハブの見た目を差し替え

   ## 確認してほしいこと
   - サイズ感が他のキャラと合っているか
   - 色味が背景と喧嘩していないか

   ## スクショ
   （ここに画像をドラッグ＆ドロップで貼れます）
   ```

   ※GitHubの説明欄は、**画像をドラッグ&ドロップでそのまま貼れます**。見た目に関わる変更のときは、変更前後のスクショを貼っておくと、確認する人がゲームを起動しなくても判断できます。

8. 「Create pull request」を押せば、PRの完成です！

   ![プルリクエストの画面](../git_images/1-11_pr_page.png)

9. PR画面には3つのタブがあります。

   - **Conversation**：コメントのやり取り。ここで相談します
   - **Commits**：このPRに含まれるコミットの一覧
   - **Files changed**：**変更されたファイルの中身が全部見られる**タブ。画像は変更前後を並べて表示できます

   確認するときのメイン画面は「Files changed」です。行にマウスを乗せると「＋」が出て、**その行に対してピンポイントでコメント**を付けられます。

   ![Files changedタブとコメント](../git_images/1-12_pr_files.png)

   ※このスクショでは、自動チェックのBotが「READMEには敵20体でクリアと書いてあるが、シーンの設定は1体になっている」と指摘しています。こういう食い違いを合流前に見つけられるのが、PRを挟む一番のメリットです。

10. PRを出したら、チームに一声かけましょう。

    > 「敵の絵のPR出しました！確認お願いします 🙏」

    GitHubからも通知は飛びますが、埋もれやすいのでDiscordなどで伝えるのが確実です。

11. 【確認する側になったら】
    難しく考えなくて大丈夫です。見るのはこの3点だけ。

    - 意図した変更だけが入っているか（関係ないファイルが混ざっていないか）
    - 明らかにおかしいところがないか
    - 自分が今触っているファイルと重なっていないか

    問題なければ「Files changed」→「Review changes」→「Approve」でOKサインを出します。
    気になる点があれば、コメントを残して「Request changes」。**分からない部分は「ここどうなってる？」と質問するだけでも十分**です。全員が同じくらいの経験値なので、遠慮なく聞き合いましょう。

12. PRが作れて、確認をお願いできたら、今回は完成です！
    次回、いよいよ合流させます。
